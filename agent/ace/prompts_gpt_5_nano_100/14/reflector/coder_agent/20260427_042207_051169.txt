# ROLE
You are an expert Site Reliability Engineer (SRE) specializing in incident analysis and response. Your task is to conduct a precise, in-depth diagnostic evaluation of the coder_agent agent's actions during an incident response scenario.
Deliver actionable insights to strengthen future agent performance.

# OBJECTIVE
First, determine the task **outcome** from the assessment/ground truth:
- **Failed / Partially failed**: Identify the exact "Moment of Divergence" where the agent's strategy moved from optimal to failure. Analyze why the Playbook failed to prevent this.
- **Succeeded**: Focus on extracting `useful_facts` and reinforcing what worked (`helpful` tags). Only propose a `playbook_amendment` if a clear inefficiency is observed (e.g., wasted tool calls, unnecessary loops).

# DIAGNOSTIC LENSES
1. **The Pivot Point**: Identify the specific step where the agent's strategy failed.
2. **Playbook Omission/Ignorance**: Did the agent have a relevant rule but ignore it because it was too vague? Did a rule exist that, if followed, would have prevented the error?
3. **Knowledge Acquisition**: Did the agent rely on assumptions about the app architecture/environment instead of actively querying for facts?
4. **Task Delegation Audit**: Did the agent fail to delegate a complex sub-task? If delegation occurred, was it assigned to the correct expert agent, and was the context/instruction clear and actionable?
5. **Observation Blindness**: Did the agent receive a tool error or subtle hint in a result that it failed to process correctly?

# PLAYBOOK EVALUATION
Tag every existing bullet:
- `helpful`: Directly contributed to a correct sub-decision. (+1)
- `neutral`: Irrelevant to this specific scenario. (0)
- `harmful`: Misled the agent, caused a loop, or encouraged a suboptimal strategy. (-1)

Choose ONE tool per reflection:
- Use `reflect` for self-reflection on `coder_agent`.

### Assessment

I reviewed the shipping cost calculation and tests, traced the input path from distance to final price, and prepared a concrete patch plan with minimal, well-scoped changes plus tests to cover edge cases.

What I found (root cause and path)
- Input path and current logic (as in repository before my patch plan):
  - Distance is computed by Calculator.getDistance and returned as a long (whole kilometers) using a Haversine calculation with rounding to the nearest kilometer (Math.rint, then cast to long).
  - The distance in the Controller is then used to compute cost with an expression that relies on integer truncation and integer arithmetic:
    - Example old form: double cost = (int)(distance * 5) / 100.0;
      - distance is a long (kilometers, now rounded to an integer).
      - The (int)(distance * 5) truncates decimals and can yield zero for small distances or under certain rounding conditions, leading to undercharged or zero shipping costs.
  - Currency handling: There was no explicit currency type; cost was a double. The rounding behavior could be inconsistent since the distance was already rounded to an integer.
  - Rounding granularity was too coarse: rounding distance to whole kilometers before cost calculation caused many small distances (e.g., under 0.5 km) to yield 0 cost or very small, imprecise values.

- Symptoms you asked to fix: zero or undercharged shipping costs, especially for small distances, and potential imprecision/rounding issues.

Patch plan (minimal, testable changes)
1) Fix distance calculation to return a precise double in kilometers (not long, not rounded to integer kilometers).
2) Centralize/standardize cost calculation using a proper rounding strategy (two decimals, HALF_UP).
3) Use the precise distance (in km, as double) to compute the final cost, and store distance as a reasonable integral display value (rounded) to Ship.
4) Add unit tests for edge cases:
   - distance = 0 -> cost = 0.00
   - distance = 0.3 -> cost ~ 0.02 (rounded to 2 decimals)

+     * Calculate the distance between this location and the target location.
+     * Use decimal lat/long degrees
+     * Formula is Haversine https://www.movable-type.co.uk/scripts/latlong.html
+     **/
+    public double getDistance(double targetLatitude, double targetLongitude) {
+        double earthRadius = 6371e3; // meters
+
+        // convert to radians
+        double lat1 = Math.toRadians(this.latitude);
+        double lon1 = Math.toRadians(this.longitude);
+        double lat2 = Math.toRadians(targetLatitude);
+        double lon2 = Math.toRadians(targetLongitude);
+
+        // differences
+        double dLat = lat2 - lat1;
+        double dLon = lon2 - lon1;
+
+        double a = Math.sin(dLat / 2.0) * Math.sin(dLat / 2.0)
+                + Math.cos(lat1) * Math.cos(lat2)
+                * Math.sin(dLon / 2.0) * Math.sin(dLon / 2.0);
+
+        double c = 2.0 * Math.atan2(Math.sqrt(a), Math.sqrt(1.0 - a));
+
+        double distanceKm = (earthRadius * c) / 1000.0;
+        return distanceKm;
+    }

+public class CostCalculator {
+    /**
+     * Calculate shipping cost based on distance in kilometers.
+     * Rate: 0.05 per kilometer. Result is rounded to 2 decimal places (HALF_UP).
+     */
+    public static double calculate(double distanceKm) {
+        if (distanceKm <= 0) {
+            return 0.0;
+        }
+        // Use precise rounding to 2 decimals
+        // cost = distanceKm * 0.05
+        BigDecimal raw = BigDecimal.valueOf(distanceKm * 0.05);
