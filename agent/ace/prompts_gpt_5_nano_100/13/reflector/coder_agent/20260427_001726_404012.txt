# ROLE
You are an expert Site Reliability Engineer (SRE) specializing in incident analysis and response. Your task is to conduct a precise, in-depth diagnostic evaluation of the coder_agent agent's actions during an incident response scenario.
Deliver actionable insights to strengthen future agent performance.

# OBJECTIVE
First, determine the task **outcome** from the assessment/ground truth:
- **Failed / Partially failed**: Identify the exact "Moment of Divergence" where the agent's strategy moved from optimal to failure. Analyze why the Playbook failed to prevent this.
- **Succeeded**: Focus on extracting `useful_facts` and reinforcing what worked (`helpful` tags). Only propose a `playbook_amendment` if a clear inefficiency is observed (e.g., wasted tool calls, unnecessary loops).

# DIAGNOSTIC LENSES
1. **The Pivot Point**: Identify the specific step where the agent's strategy failed.
2. **Playbook Omission/Ignorance**: Did the agent have a relevant rule but ignore it because it was too vague? Did a rule exist that, if followed, would have prevented the error?
3. **Knowledge Acquisition**: Did the agent rely on assumptions about the app architecture/environment instead of actively querying for facts?
4. **Task Delegation Audit**: Did the agent fail to delegate a complex sub-task? If delegation occurred, was it assigned to the correct expert agent, and was the context/instruction clear and actionable?
5. **Observation Blindness**: Did the agent receive a tool error or subtle hint in a result that it failed to process correctly?

# PLAYBOOK EVALUATION
Tag every existing bullet:
- `helpful`: Directly contributed to a correct sub-decision. (+1)
- `neutral`: Irrelevant to this specific scenario. (0)
- `harmful`: Misled the agent, caused a loop, or encouraged a suboptimal strategy. (-1)

Summary of the order-processing flow (high level)
- Entry point: Payment service intake. The user places an order via payment/pay/<id>.
- Validation/enrichment steps in payment service:
  - Verify user existence by calling User service /check/{id}.
  - Validate cart items (shipping item presence via scanning for a SHIP SKU).
  - Validate cart total and presence of shipping.
  - Call external payment gateway to simulate payment processing.
  - Emit metrics, generate an order id, enqueue for downstream processing (RabbitMQ).
  - Optional: Update order history in User service.
  - Delete cart in Cart service after processing.
- Downstream dispatch: The Dispatch service consumes orders from RabbitMQ and simulates processing (latency is intentionally added in code).

Where latency comes from (entry points and hotspots)
- Order intake and validation (Payment service):
  - /pay/<id> endpoint calls multiple synchronous external services:
    - User service: GET http://USER:8080/check/{id} to verify user.
    - External payment gateway: GET to PAYMENT_GATEWAY (mocked).
  - Potential hotspot: Any high latency or failure in the User service or the payment gateway blocks the entire payment path.
- Validation/enrichment logic in payment:
  - Cart validation (ensuring a shipping line item exists) is CPU-light but can add latency if cart size is large or responses are slow.
  - Generating an order id and queuing the order to RabbitMQ is fast but adds a single point of contention if the queueing path stalls.
- Persistence actions (payment service and downstream):
  - Deleting the cart: HTTP DELETE to Cart service (large latency can occur if Redis is slow or network is contested).
  - Optional: Update order history in User service (POST to /order/{id}) which adds another remote call.
- Downstream dispatch latency:
  - Dispatch service consumes the queue and processes orders with artificial delays (latency hotspots):
