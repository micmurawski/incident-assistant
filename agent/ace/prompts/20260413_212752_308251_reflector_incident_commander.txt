## Root Cause Analysis

### Investigation Findings

1. **Initial Symptom**: The catalogue service was returning HTTP 500 errors for all product-related endpoints, and the `/health` endpoint reported `mongo: false`.

2. **Investigation Results**:
   - **Monitoring Agent** identified recurring `MongoNetworkError` messages in catalogue service logs
   - **DevOps Agent** confirmed both MongoDB and catalogue pods were running on the same node
   - **Key Discovery**: Port mismatch - The `MONGO_URL` environment variable was configured as `mongodb://mongodb:27018/catalogue`, but the MongoDB service runs on port **27017**

3. **Root Cause**: The catalogue service was attempting to connect to MongoDB on port 27018 (wrong port), while the MongoDB service is configured to listen on port 27017. This port mismatch caused all MongoDB connection attempts to fail.

4. **Contributing Factor**: The deployment was updated with the corrected MONGO_URL, but the catalogue pod was not restarted to pick up the new configuration (restart count remained at 0).

---

## Proposed Fix

### Configuration Changes

| Configuration Item | Before | After |
|-------------------|--------|-------|
| MONGO_URL | `mongodb://mongodb:27018/catalogue` | `mongodb://172.31.65.122:27017/catalogue` |

The fix involved:
1. **Changing the port** from 27018 to 27017 to match the MongoDB service port
2. **Using the direct pod IP** (`172.31.65.122`) instead of the service name (`mongodb`) to work around DNS resolution issues in the Linkerd service mesh

### Resolution Steps

1. Updated the `MONGO_URL` in the catalogue deployment configuration
2. Triggered a rollout restart to apply the new configuration
3. Created a new pod with the corrected MongoDB connection string
