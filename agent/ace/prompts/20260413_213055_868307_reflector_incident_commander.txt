# Post-Mortem Report: Payment Service 500 Errors

## Root Cause Analysis

**Primary Root Cause:** Misconfigured AMQP_HOST environment variable

The payment service was configured to connect to a non-existent RabbitMQ service hostname (`rabbitmq-cluster`), while the actual RabbitMQ service in the cluster is named `rabbitmq`.

**Investigation Path:**
1. **Monitoring Agent** initially identified DNS resolution failures causing 500 errors, incorrectly attributing them to the dispatch service
2. **DevOps Agent** confirmed DNS was working correctly, and identified the issue was actually Linkerd proxy connection failures
3. **Coder Agent** identified the true root cause: the `AMQP_HOST` environment variable in `k8s/manifests/payment.yaml` was set to `rabbitmq-cluster` (line 34), but the actual RabbitMQ service is named `rabbitmq`

**Error Flow:**
- User submits payment → PayPal processes successfully (200) → Payment service attempts to queue order to RabbitMQ → Fails to resolve `rabbitmq-cluster` → Returns 500 to user

The incorrect hostname caused DNS resolution failures, which manifested as Linkerd proxy connection timeouts (`connect timed out after 1s`, `endpoint 169.254.1.1:42699`).

---

## Proposed Fix

Change the `AMQP_HOST` environment variable in `k8s/manifests/payment.yaml` from `rabbitmq-cluster` to `rabbitmq`:

**Before:**
```yaml
- name: AMQP_HOST
  value: rabbitmq-cluster
```

**After:**
```yaml
- name: AMQP_HOST
  value: rabbitmq
```

This aligns the payment service configuration with the actual RabbitMQ service name in the Kubernetes cluster.

---

## Execution

1. **Investigation Phase:** Agents collaborated to identify the misconfiguration through log analysis and code review
2. **Initial Fix Attempt:** The deploy_app tool was called but did not properly apply the configuration change
3. **Verification:** DevOps agent confirmed the deployment still had incorrect `AMQP_HOST: rabbitmq-cluster`
4. **Correction:** DevOps agent directly modified and applied `k8s/manifests/payment.yaml` with the correct value
5. **Verification:** Monitoring confirmed the fix was successful - new payment pod connected to RabbitMQ and order processing resumed

**Verification Metrics:**
- New payment pod successfully connects to RabbitMQ
- HTTP 200 responses returned for payment requests
- Logs show: `rabbitmq: message sent`, `queue order`, `payment for anonymous-XXXX`
- Success rate improved to ~92%

---

## Conclusion

The incident was caused by a simple configuration error - the payment service was configured to connect to a non-existent RabbitMQ hostname (`rabbitmq-cluster` instead of `rabbitmq`). This caused DNS resolution failures when attempting to queue orders after payment processing, resulting in 500 Internal Server Error responses to users.

The fix was applied by updating the `AMQP_HOST` environment variable to the correct value. Post-fix verification confirms:
- Payment service successfully connects to RabbitMQ
- Orders are being queued and processed
- Users can complete purchases successfully

**Recommendations:**
1. Add validation for service names in environment variables during deployment
2. Implement health checks that verify all required service connections at startup
3. Add retry logic in RabbitMQ publisher to handle transient connection issues
