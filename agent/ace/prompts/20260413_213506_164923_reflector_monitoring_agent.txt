## Payment Service Incident Investigation - Summary

### Root Cause Identified

**The 500 Internal Server Errors are caused by a DNS resolution failure.**

The payment service is failing to resolve a hostname (likely the dispatch service) when trying to queue orders. The error appears as:
```
ERROR in payment: [Errno -2] Name or service not known
```

### Detailed Findings

1. **Error Pattern:**
   - Error rate: **50%** (13 HTTP 500 responses out of 26 total payment requests in the last hour)
   - All 13 errors show the same error message: `[Errno -2] Name or service not known`
   - Errors occur immediately after the "queue order" log entry

2. **Timeline:** Errors started at ~21:09:33 and continued at regular intervals (~5-7 seconds apart) through 21:10:21

3. **What Works:**
   - Health check endpoint (`/health`) returns HTTP 200 consistently
   - PayPal payment processing succeeds (`https://paypal.com/ returned 200`)

4. **What Fails:**
   - Order queuing functionality - the payment service cannot resolve the hostname of the queue/dispatch service
   - This indicates a DNS or networking issue between the payment pod and the dispatch service

5. **Environment Status:**
   - Payment pod: `Running` (2/2 ready)
   - Dispatch pod: `Running` (2/2 ready)  
   - Services in application namespace are available

### Likely Causes

1. **DNS Issue:** The payment pod cannot resolve the dispatch service hostname via Kubernetes DNS
2. **Network Policy Issue:** Network connectivity blocked between payment and dispatch namespaces
3. **Service Name Misconfiguration:** Payment service may be configured with wrong service hostname

### Recommended Actions

1. **Verify DNS resolution** from payment pod to dispatch service:
   ```bash
   kubectl exec -it payment-pod -n application -- nslookup dispatch
   ```

2. **Check network policies** for any blocking rules between payment and dispatch

3. **Verify dispatch service endpoints** are properly registered:

   ```bash
   kubectl get endpoints dispatch -n application
   ```
